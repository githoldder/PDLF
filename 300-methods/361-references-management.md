# 参考文献管理规范

> **参考文献不是链接的堆砌，而是问题树和风险树的证据支撑。**
>
> 每条引用都必须回答：它证明了哪个节点的哪个结论？

---

## 核心原则

### 原则 1：一一映射

每条参考文献必须与 Problem Tree 或 Risk Tree 的**具体节点**一一对应。

```
❌ 错误做法：
## 参考资料
- [Stack Overflow](https://...)
- [官方文档](https://...)
- [技术博客](https://...)

✅ 正确做法：
## 节点 [根因] DATE(created_at) 导致索引失效
- **证据**: REF-001 (Stack Overflow, 284 upvotes)
- **验证**: REF-007 (MySQL 官方文档)
- **补充**: REF-012 (GitHub Issue, 含复现步骤)
```

### 原则 2：可追溯

任何结论被质疑时，能在 30 秒内找到支撑它的参考文献。

### 原则 3：可验证

每条参考文献必须有验证标记（投票数、官方确认、多人复现等）。

## 引用编号系统

### 全局编号规则

```
REF-{NNNN}
```

| 段 | 含义 | 示例 |
|---|------|------|
| `REF` | 固定前缀 | REF |
| `NNNN` | 全局序号，跨问题连续递增 | 0001, 0002, ... |

### 为什么用全局编号？

- **跨问题复用**：同一个参考文献可以被多个问题引用
- **知识图谱**：可以构建"哪些问题引用了同一篇文献"的反向索引
- **Agent 识别**：Agent 可以直接通过 REF-NNNN 调用已有知识

## 引用与节点的映射格式

### 在 problem.md 中的标注

```markdown
## Diagnose

1. **Why** 接口变慢? → 数据库查询耗时增加
   - **证据**: REF-0001 ([Stack Overflow: MySQL slow query诊断](references/0001-stackoverflow-mysql-slow-query.md))
   
2. **Why** 查询耗时增加? → 订单表走了全表扫描
   - **证据**: REF-0002 ([GitHub Issue: ORM 生成查询分析](references/0002-github-orm-query.md))
   - **验证**: REF-0003 ([MySQL EXPLAIN 官方文档](references/0003-mysql-docs-explain.md))

3. **Why** 没走索引? → 查询条件用了 `DATE(created_at)` 函数
   - **证据**: REF-0004 ([Stack Overflow: DATE() index skip](references/0004-stackoverflow-date-index.md))
   - **深度**: REF-0005 ([MySQL 索引原理博客](references/0005-blog-mysql-index.md))
```

### 在 risk.md 中的标注

```markdown
## 失效模式 1：函数包裹索引列

- **触发条件**: ORM 自动生成 DATE(column) 查询
  - **案例**: REF-0006 ([GitHub Issue: Django ORM DATE()](references/0006-github-django-orm.md))
  - **频率**: REF-0007 ([Stack Overflow 统计](references/0007-stackoverflow-stats.md))
- **影响**: 全表扫描 → P99 飙升
  - **量化**: REF-0008 ([性能测试报告](references/0008-perf-test.md))
```

## 参考文献文件模板

### 文件位置

```
/problem-tree/
├── problem.md
├── risk.md
└── references/
    ├── 0001-stackoverflow-mysql-slow-query.md
    ├── 0002-github-orm-query.md
    ├── 0003-mysql-docs-explain.md
    └── ...
```

### 文件命名规范

```
{NNNN}-{source}-{keywords}.md
```

### 文件内容结构

```markdown
# REF-{NNNN}: [标题]

## 元信息
- **编号**: REF-{NNNN}
- **来源平台**: [Stack Overflow / GitHub / 官方文档 / 博客 / 论文]
- **URL**: [完整链接]
- **获取时间**: [YYYY-MM-DD]
- **作者/回答者**: [用户名或机构]
- **作者可信度**: [专家标签 / 官方账号 / 普通用户]

## 内容摘要
- **原文问题**: [一句话概括原文在解决什么问题]
- **核心结论**: [一句话总结核心观点]
- **关键数据/代码**: [摘录关键证据]

## 验证信息
- **投票数/星标**: [N upvotes / N stars]
- **采纳状态**: [被采纳 / 未被采纳 / 官方回复]
- **社区验证**: [多人确认 / 单一来源 / 有争议]
- **时效性**: [最新 / 较新 / 过时]

## 映射关系
- **对应 Problem Tree 节点**: [节点路径，如 "Diagnose > 根因 > DATE(created_at)"]
- **对应 Risk Tree 节点**: [节点路径，如 "失效模式 1 > 触发条件"]
- **适用阶段**: [Discover / Triage / Diagnose / Transform / Solve / Verify / Learn]

## 可信度评估
| 维度 | 评分 (1-5) | 说明 |
|------|-----------|------|
| 专业度 | ⭐⭐⭐⭐⭐ | 回答者有 MySQL 专家标签 |
| 时效性 | ⭐⭐⭐⭐ | 2023 年，适用于 MySQL 8.0 |
| 可复现 | ⭐⭐⭐⭐⭐ | 提供了完整的 EXPLAIN 验证步骤 |
| 社区验证 | ⭐⭐⭐⭐ | 284 upvotes，15+ 条验证评论 |

## 引用场景
- **当前问题**: [问题 ID，如 PDLF-20261001-001]
- **引用次数**: [N]（被多少个问题引用过）
- **相似问题**: [问题 ID 列表]

## 备注
- [任何补充信息]
- [版本兼容性说明]
- [已知局限性]
```

## 引用类型标记

在 problem.md 中，不同类型的引用用不同标记：

| 标记 | 含义 | 使用场景 |
|------|------|---------|
| **证据** | 直接支撑当前节点结论 | 核心论点必须有 |
| **验证** | 从另一来源确认同一结论 | 增强可信度 |
| **补充** | 提供额外背景或细节 | 非必需但有帮助 |
| **对比** | 提供不同观点或方法 | Transform 阶段方案对比 |
| **反例** | 说明某种方法不行 | 同样珍贵，避免踩坑 |

## 质量检查清单

在归档参考文献前，检查：

- [ ] **编号唯一**：全局不重复
- [ ] **链接有效**：URL 可访问（至少在当时可访问）
- [ ] **映射完整**：至少关联一个 Problem Tree 或 Risk Tree 节点
- [ ] **验证标记**：有投票数、采纳状态或其他可信度指标
- [ ] **摘要独立**：不看原文也能理解核心结论
- [ ] **代码可运行**：如果是代码片段，确保在当前环境可运行

## 一句话总结

> **参考文献管理的本质，是把"别人的经验"变成"你的证据"。**
>
> 不是收藏链接，是建立可验证的认知支撑网络。
