# V-Model 映射

> **不要等开发结束才开始思考验证，而是在每个抽象层级上预先建立对应的验证方式。**

---

## V-Model 结构

```
需求分析    ←────────────────────────→    验收测试
    ↑                                          │
    │         每个"我们认为正确"的，              │
    │         都必须有方式尝试证明它不正确          │
    │                                          ↓
系统设计    ←────────────────────────→    系统测试
    ↑                                          │
    │                                          ↓
详细设计    ←────────────────────────→    集成测试
    ↑                                          │
    │                                          ↓
编码        ←────────────────────────→    单元测试
```

---

## PDLF 阶段映射

| V-Model 层级 | PDLF 阶段 | 活动 |
|-------------|----------|------|
| 需求分析 | **DISCOVER** + **TRIAGE** | 捕捉用户真正需要什么 |
| 需求分析 | **DIAGNOSE** | 对每个需求做 5Why — 这是真正的需求吗？ |
| 系统设计 | **TRANSFORM** | 将需求重述为系统能力 |
| 详细设计 | **TRANSFORM** | 将能力分解为组件契约 |
| 编码 | **SOLVE** | 实现 + 单元测试 |
| 单元测试 | **Risk Tree** | 这个函数可能怎么坏？ |
| 集成测试 | **Risk Tree** | 组件连接时可能怎么坏？ |
| 系统测试 | **Risk Tree** | 全系统规模下可能怎么坏？ |
| 验收测试 | **VERIFY** | 这真的解决了最初的问题吗？ |

---

## 关键洞察

> **PDLF 确保左侧（设计）正确后，右侧（验证）才有意义。**

没有清晰的问题定义，测试只是在验证"我们是否正确地做错了事"。

---

## 实践建议

1. **每个设计文档必须链接到对应的 Risk Tree**
   - 系统设计 → `risks/system-level.risk.md`
   - 详细设计 → `risks/integration-level.risk.md`

2. **验收标准必须追溯到原始问题**
   - 验收测试通过 ≠ 问题解决
   - 必须回到 Discover 阶段验证症状是否消失

3. **Risk Tree 定期复审**
   - 每次迭代回顾时，检查是否有新的风险模式出现
   - 已关闭的风险，如果条件变化，重新打开
