# Triage 检查清单

> **"不解决"本身也是一个工程决策。**

---

## 快速判断：4 个维度

| 维度 | 问题 | 低（1-3） | 中（4-6） | 高（7-10） |
|------|------|----------|----------|----------|
| **Impact** | 不解决会造成什么？ | 轻微不便 | 功能降级 | 核心功能丧失 |
| **Urgency** | 需要现在解决吗？ | 可以延后 | 本周处理 | 立即处理 |
| **Scope** | 影响多少对象/链路？ | 单个用户 | 部分用户 | 所有用户 |
| **Uncertainty** | 我们是否还不了解它？ | 充分理解 | 部分不确定 | 完全未知 |

---

## 决策矩阵

```
                 高 Impact
                    │
         立即处理   │   计划处理
            ↓      │      ↓
    ┌──────────────┼──────────────┐
高  │   紧急重要    │   重要不紧急  │
Urg │   P0/P1      │   P2         │
    ├──────────────┼──────────────┤
低  │   紧急不重要  │   不紧急不重要│
    │   委托/快速修 │   接受风险    │
    └──────────────┼──────────────┘
                    │
                 低 Impact
```

---

## Triage 决策选项

| 决策 | 适用场景 | 后续动作 |
|------|---------|---------|
| **立即处理** | 高 Impact + 高 Urgency | 进入 Diagnose |
| **计划处理** | 高 Impact + 低 Urgency | 排入 backlog，设定 deadline |
| **快速修复** | 低 Impact + 高 Urgency | 最小成本修复，不深入根因 |
| **接受风险** | 低 Impact + 低 Urgency | 记录到 risk.md，持续监控 |
| **删除** | 已过时 / 已无关 | 归档，说明原因 |

---

## Re-Triage 触发条件

Diagnose 后必须重新评估：

- [ ] 根因是否与预期一致？
- [ ] 影响范围是否扩大或缩小？
- [ ] 解决方案的成本是否可接受？
- [ ] 是否存在更高优先级的关联问题？

---

## 示例

### 初筛
```
问题: API 响应变慢
Impact: 高（核心交易链路）
Urgency: 高（所有用户受影响）
Scope: 广（全平台）
Uncertainty: 中（已知症状，未知根因）
决策: ✅ 立即处理
```

### Re-Triage（Diagnose 后）
```
根因: 新功能引入的查询模式导致索引失效
影响范围: 比预期更广（所有使用 DATE() 函数的查询）
解决方案成本: 低（改写查询，零风险）
关联问题: 可能存在其他类似查询模式
Re-Triage 决策: ✅ 升级为 P0，同时扫描全库类似查询
```
