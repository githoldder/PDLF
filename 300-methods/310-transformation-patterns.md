# 问题转化模式 (Problem Transformation Patterns)

> **目标**: 把一个困难问题，重述为一个更简单、等价、或近似等价的问题。

---

## 模式 1: 约束松弛 (Constraint Relaxation)

**核心**: 去掉一个约束，解决简化版，再逐步加回来。

| | 内容 |
|---|------|
| 原问题 | "找到避开所有收费站的最短路径" |
| 松弛后 | "找到最短路径" → 然后过滤掉含收费站的路段 |
| 适用 | 约束使问题 NP-hard，松弛后有多项式解法 |

---

## 模式 2: 降维 (Dimensionality Reduction)

**核心**: 投影到更低维度的子问题。

| | 内容 |
|---|------|
| 原问题 | "优化整个供应链" |
| 降维后 | "先优化仓库到门店的配送段" |
| 适用 | 高维问题有天然模块化结构 |

---

## 模式 3: 类比映射 (Analogy Mapping)

**核心**: 映射到另一个领域已解决的问题。

| | 内容 |
|---|------|
| 原问题 | "如何确定 Bug 修复优先级？" |
| 类比 | "RICE 评分用于功能优先级" → 改编为 Bug 版 RICE |
| 适用 | 问题本质与已知模型同构 |

---

## 模式 4: 固定常数 (Divide by Constant)

**核心**: 假设某个参数固定，求解后再推广。

| | 内容 |
|---|------|
| 原问题 | "系统如何支撑 100 万并发用户？" |
| 固定后 | "先支撑 1 万用户" → 测出瓶颈 →  extrapolate |
| 适用 | 规模/参数导致问题复杂化 |

---

## 模式 5: 最坏界 (Worst-Case Bounding)

**核心**: 不求精确解，求上下界。

| | 内容 |
|---|------|
| 原问题 | "精确计算所有网络条件下的延迟" |
| 界化后 | "99 分位延迟 < 100ms" |
| 适用 | 精确解计算成本过高，界已足够决策 |

---

## 模式 6: 模拟替代 (Simulation Substitution)

**核心**: 解析解难求时，用模拟代替。

| | 内容 |
|---|------|
| 原问题 | "推导出用户流失率的闭式表达式" |
| 模拟后 | "用历史数据做蒙特卡洛模拟" |
| 适用 | 系统动态复杂，解析模型难以建立 |

---

## 模式 7: 逆问题 (Inverse Problem)

**核心**: 从"求 X 给定 Y"转为"给定 X，Y 应该是什么"。

| | 内容 |
|---|------|
| 原问题 | "系统为什么慢？" |
| 逆问题 | "如果数据库是瓶颈，我们会观察到什么症状？" → 对照实际 |
| 适用 | 正向诊断路径过多，逆向验证更高效 |

---

## 模式 8: Oracle 归约 (Oracle Reduction)

**核心**: 假设存在一个完美子程序，先设计系统架构，再实现该子程序。

| | 内容 |
|---|------|
| 原问题 | "构建一个推荐引擎" |
| Oracle | "假设我们有完美的用户相似度函数" → 设计 API → 实现相似度计算 |
| 适用 | 问题耦合度高，分离关注点降低复杂度 |

---

## 停止转化的信号

✅ 问题可以在 2 分钟内被有能力的工程师解决  
✅ 问题可分解为 ≤3 个清晰的子任务  
✅ 验收标准明确且可验证  

---

> **5Why 是纵向寻找问题，问题转化是横向简化问题。**
