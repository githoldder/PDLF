# 问题状态层级：L0 → L3

> **异常 ≠ 问题。问题的重要性不是由"它现在看起来多严重"决定，而是由定位后的因果结构决定。**

---

## 四层状态

| 层级 | 状态 | 核心问题 | 核心动作 | 示例 |
|------|------|---------|---------|------|
| **L0** | 信号 (Signal) | "这只是现象吗？" | 观察，不判断 | "CPU 90%" |
| **L1** | 候选问题 (Candidate) | "这值得处理吗？" | 初筛判断 | "查询慢导致超时" |
| **L2** | 关键问题 (Problem) | "真正的问题是什么？" | 定位 + 转化 + 解决 | "索引失效导致全表扫描" |
| **L3** | 系统性风险 (Risk) | "这类问题还会发生吗？" | 验证 + 预防 + 沉淀 | "ORM 自动生成函数查询是系统性模式" |

---

## 状态跃迁

### 跃迁 1：L0 → L1（信号 → 候选问题）

```
"服务器 CPU 90%"  →  初步判断：可能有问题  →  生成 Problem Candidate
```

关键动作：**不做过度判断**。L0 只是现象，L1 才开始判断是否值得投入。

### 跃迁 2：L1 → L2（候选 → 关键问题）

```
"查询慢导致超时"  →  5Why 定位  →  "索引失效导致全表扫描"  →  可行动
```

关键动作：**Diagnose**。通过 5Why、鱼骨图、故障树等方法找到真正的问题。

### 跃迁 3：L2 → L3（关键问题 → 系统性风险）

```
"索引失效"  →  发现是"函数包裹索引列"的系统性模式  →  影响未来所有类似查询
```

关键动作：**Learn**。从单点问题中提取系统性模式，录入 Risk Tree。

### 反向跃迁：L1 → L0（严重现象 → 只是信号）

```
"严重报错"  →  定位后发现只是测试环境的一个边缘功能  →  接受风险 / 删除
```

关键动作：**Re-Triage**。定位后重新评估，"不解决"本身也是一个工程决策。

## 关键洞察

### 洞察 1：层级越高，价值越大

| 层级 | 解决一个问题 | 预防一类问题 |
|------|-------------|-------------|
| L0 | 忽略 | — |
| L1 | 单点修复 | — |
| L2 | 根因修复 | 短期有效 |
| L3 | 模式修复 | **长期免疫** |

### 洞察 2：反向跃迁同样重要

不是每个信号都值得升级。学会**降级**（接受风险、删除、延后）和学会升级一样重要。

> "不解决"本身也是一个工程决策。

### 洞察 3：L3 是循环的燃料

每次到达 L3，都会沉淀一个 Risk Pattern。这个 Pattern 会在下一次 Discover 阶段被匹配，从而实现**提前发现**。

```
新问题
  ↓
Discover → 匹配历史 Risk Pattern → 提前识别 → 在 L1 阶段就拦截
```

这就是组织学习能力的来源。
