# 问题命名与规范

> **命名即思考。一个好的问题命名，本身就是一次初步的 Diagnose。**

---

## 问题 ID 编码规则

### 格式

```
PDLF-{YYYYMMDD}-{NNN}
```

| 段 | 含义 | 示例 |
|---|------|------|
| `PDLF` | 框架标识 | 固定前缀 |
| `YYYYMMDD` | 发现日期 | 20261001 |
| `NNN` | 当日序号 | 001 |

### 示例

```
PDLF-20261001-001  ← 2026-10-01 发现的第 1 个问题
PDLF-20261001-002  ← 2026-10-01 发现的第 2 个问题
PDLF-20261002-001  ← 2026-10-02 发现的第 1 个问题
```

### 变体（子问题）

```
PDLF-20261001-001-A  ← 主问题的子问题 A
PDLF-20261001-001-B  ← 主问题的子问题 B
```

## 问题命名规范

### 好命名的特征

| 特征 | 好示例 | 坏示例 |
|------|--------|--------|
| 具体 | "API P99 从 120ms 飙升到 3200ms" | "系统有点慢" |
| 可观测 | "订单表全表扫描导致查询超时" | "感觉数据库有问题" |
| 无归因 | "DATE(created_at) 导致索引失效" | "开发写了个烂查询" |
| 可验证 | "P99 > 200ms 持续 5 分钟" | "偶尔有点卡" |

### 命名模板

```
[对象] + [现象] + [影响]
```

**示例**:
- ✅ `/api/v1/orders P99 延迟从 120ms 飙升到 3200ms，影响所有用户`
- ✅ `DATE(created_at) 函数导致索引失效，订单查询全表扫描`
- ❌ `系统慢`（太模糊）
- ❌ `开发写了烂代码`（归因于人）

## 优先级定义

### P0-P3 四级优先级

| 级别 | 名称 | 定义 | 响应时间 | 示例 |
|------|------|------|---------|------|
| **P0** | 紧急 | 核心功能完全不可用，影响所有用户 | 立即（< 1h） | 核心交易链路中断 |
| **P1** | 高 | 核心功能降级，影响部分用户 | 当日（< 4h） | P99 飙升，用户可感知 |
| **P2** | 中 | 非核心功能问题，有 workaround | 本周（< 3d） | 报表生成慢，可手动导出 |
| **P3** | 低 | 体验优化，不影响功能 | 排期（< 2w） | UI 对齐偏差 |

### 优先级升级/降级规则

```
初筛优先级
    ↓
Diagnose 后 Re-Triage
    ↓
可能升级（发现系统性影响）
可能降级（发现只是边缘问题）
```

## 复杂度评分

### 1-10 分制

| 分数 | 含义 | 判断标准 |
|------|------|---------|
| 1-3 | 简单 | 单一文件修改，无需测试，< 30 分钟 |
| 4-6 | 中等 | 多文件修改，需要测试，< 1 天 |
| 7-8 | 复杂 | 跨系统修改，需要设计评审，< 1 周 |
| 9-10 | 极复杂 | 架构级变更，需要方案评审，> 1 周 |

### 复杂度与优先级的关系

```
高优先级 + 低复杂度 = 立即做（快速胜利）
高优先级 + 高复杂度 = 需要 Transform（分解或转化）
低优先级 + 低复杂度 = 顺手做
低优先级 + 高复杂度 = 延后或接受风险
```

## 重要性定义

> 重要性 ≠ 优先级。重要性是对系统目标的长期影响，优先级是当前的紧急程度。

### 重要性评估

| 维度 | 问题 |
|------|------|
| **业务影响** | 不解决会影响收入/用户留存吗？ |
| **技术债务** | 不解决会累积更多问题吗？ |
| **安全风险** | 不解决会有安全隐患吗？ |
| **团队效率** | 不解决会降低团队效率吗？ |

### 重要性 vs 优先级矩阵

```
        高重要性
            │
   计划处理  │   立即处理
      ↓      │      ↓
┌───────────┼───────────┐
│ 重要不紧急 │  重要且紧急 │
│  技术债务  │   P0/P1    │
├───────────┼───────────┤
│ 不重要不紧急│ 紧急不重要 │
│   延后    │  快速修复   │
└───────────┼───────────┘
            │
        低重要性
```

## 关联性定义

### 关联类型

| 类型 | 含义 | 示例 |
|------|------|------|
| **父子** | 一个大问题拆分为多个子问题 | PDLF-001 拆分出 PDLF-001-A、PDLF-001-B |
| **依赖** | 解决 A 必须先解决 B | PDLF-003 依赖 PDLF-002 |
| **相似** | 根因相同或相似 | PDLF-004 与 PDLF-001 都是"索引失效"模式 |
| **触发** | A 的发生触发了 B | PDLF-005 的修复引入了 PDLF-006 |

### 关联表示法

在 problem.md 头部标注：

```markdown
---
**问题 ID**: PDLF-20261001-001
**优先级**: P0
**复杂度**: 3/10
**重要性**: 高
**关联**:
  - 子问题: PDLF-20261001-001-A
  - 相似: PDLF-20260928-003（同为索引失效模式）
  - 风险: [risk.md](risk.md)
---
```

## 完整头部模板

```markdown
# Problem: [问题命名]

> **问题 ID**: PDLF-{YYYYMMDD}-{NNN}
> **优先级**: P{0-3}
> **复杂度**: {1-10}/10
> **重要性**: {高/中/低}
> **状态**: {待处理/进行中/已解决/已关闭}
> **关联**: [子问题/依赖/相似/风险]

---
```

## 对鱼骨图/故障树的结构化增强

### 问题节点命名规范

每个节点应该有明确的"类型标签"：

```markdown
- [表象] P99 3200ms
  - [现象] 查询耗时增加
    - [直接原因] 全表扫描
      - [结构原因] 索引失效
        - [根因] DATE(created_at)
          - [因果节点] 测试数据量不足
```

### 类型标签定义

| 标签 | 含义 | 特征 |
|------|------|------|
| `[表象]` | 用户/监控可感知的现象 | 可观测、可量化 |
| `[现象]` | 技术层面的具体表现 | 可通过工具检测 |
| `[直接原因]` | 触发问题的最近因 | 通常是一个具体事件 |
| `[结构原因]` | 系统/设计层面的原因 | 是多个问题的共同原因 |
| `[根因]` | 最深层的可改变原因 | 改变它问题不再发生 |
| `[因果节点]` | 可永久解决的节点 | 可行动、可验证 |

### 故障树的逻辑门标注

```markdown
## Risk Tree

- [OR] 生产环境性能下降
  - [AND] 函数包裹索引列
    - [条件] ORM 自动生成 DATE(column)
    - [条件] 开发者未检查查询计划
  - [AND] 联合索引顺序错误
    - [条件] 开发者不熟悉最左前缀
    - [条件] 缺少 SQL Review
```

| 逻辑门 | 含义 | 示例 |
|--------|------|------|
| `[OR]` | 任一子节点发生即可触发父节点 | 多种原因导致同一结果 |
| `[AND]` | 所有子节点同时发生才触发父节点 | 需要多个条件同时满足 |
| `[条件]` | AND 门的必要条件 | 触发父节点的前提 |

---

## 一句话总结

> **好的命名 = 具体 + 可观测 + 无归因 + 可验证。**
>
> **好的结构 = 类型标签 + 逻辑门 + 关联关系。**
>
> 这不仅是规范，更是强迫思考的框架。
